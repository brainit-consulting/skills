# The generated server

Last verified: 2026-08-16

**Purpose:** Turn the routes `discovery.md` found and the credential `credentials.md` proved into a small MCP server that lives in one folder inside the owner's repository, runs locally over stdio, and can only do the handful of things that were agreed.

Everything below was run, except where a section says otherwise. The worked example is the folder that was generated for the `django_api` fixture, registered with `claude mcp add`, and driven by a real client; every block of output is pasted from that run.

> **Shell:** the commands assume a POSIX shell. On Windows run them in Git Bash or WSL. Measured on Node 22.22.3 with `@modelcontextprotocol/sdk` 1.30.0 and `zod` 4.4.3.

---

## Generated, not copied

The tools carry this app's verbs, parameters and shapes. A single `call_endpoint(path, method, body)` tool looks generated and is a template in disguise: it moves every decision to runtime and leaves the user nothing to review. **If you find yourself writing one, the discovery step did not finish.**

This file is a specification with worked examples, not a file to copy. Two runs of this skill should produce servers that differ only where the apps differ.

The test is whether the owner can read the tool list and recognise their own application in it. `list_orders(limit)`, `get_order(id)`, `create_order(customer, total)` is a description of what the assistant may do. `call_endpoint(path, method, body)` is a description of HTTP.

---

## What gets generated

One folder, `agent-access/`, at the root of the owner's repository. Nothing outside it is touched — not one file they wrote.

| File | What it holds |
|---|---|
| `tools.ts` | One exported object per tool: its name, its schema, and the function that calls the app |
| `server.ts` | Loads the environment, registers the tools by name, speaks stdio |
| `package.json` | The three runtime dependencies and a `start` script |
| `tsconfig.json` | So `npx tsc --noEmit` checks the folder with no arguments |
| `.env` | The credential. Gitignored |
| `.env.example` | The same keys with the values blank. Committed |
| `.gitignore` | `.env`, `calls.log`, `node_modules/` |
| `README.md` | What was built, which path each tool uses, and what the owner agreed to |
| `calls.log` | Written at runtime, one JSON line per call. Gitignored |

The folder is deletable. Removing it returns the app to exactly what it was, and that is worth saying to the owner in those words — it is the difference between this and a change to their codebase.

## The worked example: `django_api`

### What the earlier steps handed over

`discovery.md` enumerated six routes from one `router.register` line. All six answer on this app — unlike `django_shop`, where the two format-suffix routes return 500. The two the tools use:

```
GET,POST               /api/^orders/$                    order-list
DELETE,GET,PATCH,PUT   /api/^orders/(?P<pk>[^/.]+)/$     order-detail
```

(`^` and `$` are regex anchors, not part of the URL; `discovery.md` explains the output format.)

`credentials.md` established the mechanism: DRF `TokenAuthentication`, a dedicated `agent` user, and the header `Authorization: Token <key>` — **not `Bearer`**. Measured on this app, a valid key with the wrong scheme word:

```
$ curl -s -H "Authorization: Bearer $K" http://127.0.0.1:8003/api/orders/
{"detail":"Authentication credentials were not provided."}
```

The capability list agreed at interview step 3 was: **list orders, read one order, create an order.** Three tools. The router also serves `DELETE`, `PUT` and `PATCH`; none of them became a tool, because none of them was asked for.

### `agent-access/tools.ts`

```ts
// Generated by the bring-your-own-agent skill for django_api.
// Edits nothing in the app: this folder talks to it over HTTP only.

import { appendFileSync } from "node:fs";
import { dirname, join } from "node:path";
import { fileURLToPath } from "node:url";
import { z } from "zod";

const HERE = dirname(fileURLToPath(import.meta.url));
const LOG_FILE = join(HERE, "calls.log");

const BASE_URL = process.env.APP_BASE_URL ?? "http://127.0.0.1:8003";
const TOKEN = process.env.APP_API_TOKEN;

/** The most rows any list tool will ever return. */
export const MAX_LIMIT = 50;

if (!TOKEN) {
  // Fail at start-up with the cause named. Without this the header goes out as
  // the literal "Token undefined" and DRF answers {"detail":"Invalid token."} -
  // which means the value is wrong, so the next hour goes on rotating a token
  // that was fine. Measured against this app.
  throw new Error(
    "APP_API_TOKEN is not set. It belongs in agent-access/.env " +
      "(see agent-access/README.md). Nothing was started.",
  );
}

/** One JSON line per call: what was asked, and how it went. Never the token. */
function log(tool: string, args: unknown, outcome: string) {
  appendFileSync(
    LOG_FILE,
    JSON.stringify({ at: new Date().toISOString(), tool, args, outcome }) + "\n",
  );
}

/**
 * django_api authenticates with DRF TokenAuthentication. The scheme word is
 * `Token`, not `Bearer`; `Bearer` returns a 401 identical to sending no header.
 * Paths keep their trailing slash - /api/orders returns 301, /api/orders/ 200.
 */
async function api(path: string, init: RequestInit = {}): Promise<Response> {
  return fetch(`${BASE_URL}${path}`, {
    ...init,
    headers: {
      Authorization: `Token ${TOKEN}`,
      "Content-Type": "application/json",
      ...(init.headers ?? {}),
    },
    redirect: "error",
  });
}

/**
 * Copy out the fields this app's Order actually has, one at a time.
 * Never `...row`: a column added to the model later would be forwarded to the
 * agent the day it is added, with nothing in this file changing to say so.
 */
function shapeOrder(row: Record<string, unknown>) {
  return {
    id: row.id,
    customer: row.customer,
    total: row.total,
    created_at: row.created_at,
  };
}

function ok(value: unknown) {
  return { content: [{ type: "text" as const, text: JSON.stringify(value, null, 2) }] };
}

function failed(message: string) {
  return { content: [{ type: "text" as const, text: message }], isError: true };
}

export const listOrders = {
  name: "list_orders",
  config: {
    title: "List orders",
    description: `Return the most recent orders, newest first. At most ${MAX_LIMIT} rows.`,
    inputSchema: {
      limit: z
        .number()
        .int()
        .min(1)
        .max(MAX_LIMIT)
        .default(20)
        .describe(`How many orders to return (1-${MAX_LIMIT}).`),
    },
    annotations: { readOnlyHint: true },
  },
  handler: async ({ limit }: { limit: number }) => {
    // Second cap. The schema stops a caller asking for 5000; this stops the app
    // answering with 5000. django_api's list endpoint is unpaginated and ignores
    // an unknown ?limit= silently, returning every row with a 200.
    const capped = Math.min(limit, MAX_LIMIT);
    const res = await api(`/api/orders/?limit=${capped}`);
    if (!res.ok) {
      log("list_orders", { limit: capped }, `error http_${res.status}`);
      return failed(`The app returned HTTP ${res.status}: ${await res.text()}`);
    }
    const rows = (await res.json()) as Record<string, unknown>[];
    const page = rows.slice(0, capped).map(shapeOrder);
    log("list_orders", { limit: capped }, `ok ${page.length} of ${rows.length} rows`);
    return ok(page);
  },
};

export const getOrder = {
  name: "get_order",
  config: {
    title: "Get one order",
    description: "Return a single order by its id.",
    inputSchema: {
      id: z.number().int().positive().describe("The order's id."),
    },
    annotations: { readOnlyHint: true },
  },
  handler: async ({ id }: { id: number }) => {
    const res = await api(`/api/orders/${id}/`);
    if (!res.ok) {
      log("get_order", { id }, `error http_${res.status}`);
      return failed(`The app returned HTTP ${res.status}: ${await res.text()}`);
    }
    const row = (await res.json()) as Record<string, unknown>;
    log("get_order", { id }, "ok");
    return ok(shapeOrder(row));
  },
};

export const createOrder = {
  name: "create_order",
  config: {
    title: "Create an order",
    description:
      "Create an order through the app's own API, so the app's validation and " +
      "rules apply. Returns the created order.",
    inputSchema: {
      // These bounds are the app's, read off orders/models.py and
      // orders/serializers.py - CharField(max_length=200) and
      // DecimalField(max_digits=10, decimal_places=2).
      customer: z.string().min(1).max(200).describe("The customer's name."),
      total: z
        .string()
        .regex(/^\d{1,8}(\.\d{1,2})?$/)
        .describe('The order total, as a decimal string, e.g. "24.50".'),
    },
    annotations: { readOnlyHint: false, destructiveHint: false, idempotentHint: false },
  },
  handler: async ({ customer, total }: { customer: string; total: string }) => {
    const res = await api("/api/orders/", {
      method: "POST",
      body: JSON.stringify({ customer, total }),
    });
    if (!res.ok) {
      log("create_order", { customer, total }, `error http_${res.status}`);
      return failed(`The app returned HTTP ${res.status}: ${await res.text()}`);
    }
    const row = (await res.json()) as Record<string, unknown>;
    log("create_order", { customer, total }, `ok created id=${row.id}`);
    return ok(shapeOrder(row));
  },
};

// There is no delete_order tool, and the omission is deliberate: this app's
// router does serve DELETE /api/orders/<id>/. Throwing work away is a decision
// for a person, in the app, where they can see what they are throwing away.
```

### `agent-access/server.ts`

```ts
// Generated by the bring-your-own-agent skill for django_api.
// Runs locally over stdio: the client starts this process, talks to it on
// stdin/stdout, and nothing listens on a port.

import { config } from "dotenv";
import { dirname, join } from "node:path";
import { fileURLToPath } from "node:url";

const HERE = dirname(fileURLToPath(import.meta.url));

// Load .env by absolute path. An MCP client starts this process with whatever
// working directory it likes, and a bare config() reads process.cwd()/.env.
// Measured with the process started from another directory: ENOENT, and
// APP_API_TOKEN undefined - with no message on stdout or stderr.
config({ path: join(HERE, ".env"), quiet: true });

// Imported after the .env is loaded, because tools.ts reads the token at
// module scope. A plain top-level import would run before config().
const { McpServer } = await import("@modelcontextprotocol/sdk/server/mcp.js");
const { StdioServerTransport } = await import(
  "@modelcontextprotocol/sdk/server/stdio.js"
);
const { listOrders, getOrder, createOrder } = await import("./tools.js");

const server = new McpServer({ name: "django-api-agent-access", version: "1.0.0" });

// Registered one by one, on purpose. The list of what this assistant can do is
// three lines someone can read, not a loop over a directory.
server.registerTool(listOrders.name, listOrders.config, listOrders.handler);
server.registerTool(getOrder.name, getOrder.config, getOrder.handler);
server.registerTool(createOrder.name, createOrder.config, createOrder.handler);

// stdout is the protocol channel. Anything printed there that is not a JSON-RPC
// message corrupts the stream and the client reports a parse error rather than
// whatever printed it. Diagnostics go to stderr.
console.error("agent-access: 3 tools, stdio");

await server.connect(new StdioServerTransport());
```

**`.js` in `await import("./tools.js")` is correct and is not a typo.** The file on disk is `tools.ts`; Node's ES module resolution wants the *emitted* specifier. Measured, `tsx` runs all three of `"./tools"`, `"./tools.ts"` and `"./tools.js"` without complaint, so this is not something a test run will catch — it is the typecheck that catches it, which is the argument for running one:

```
./tools     TS2835: Relative import paths need explicit file extensions ... Did you mean './tools.js'?
./tools.ts  TS5097: An import path can only end with a '.ts' extension when 'allowImportingTsExtensions' is enabled.
./tools.js  (clean)
```

Both messages name the fix, which is why this costs a minute rather than an hour — provided anybody ran `tsc` at all, **and provided `tsconfig.json` says `nodenext`**. See that file below; under `moduleResolution: "bundler"` none of these errors appears.

**Registering three tools by hand, rather than looping over an array, is also deliberate**, and it has a mechanical reason as well as a readability one. A heterogeneous array of tool objects collapses to a union type, and `registerTool` then infers its generic from the first element. Measured: the loop version fails `tsc --strict` with `Property 'limit' is optional in type ... but required in type ...`, an error that names `limit` and has nothing to do with `limit`.

### `agent-access/tsconfig.json`

Small, and **not** a formality — the `.js` argument above holds only while `module` and `moduleResolution` are both `nodenext`, so a config that moves them together quietly removes the check:

```json
{
  "compilerOptions": {
    "module": "nodenext",
    "moduleResolution": "nodenext",
    "target": "es2022",
    "strict": true,
    "skipLibCheck": true,
    "noEmit": true
  },
  "include": ["server.ts", "tools.ts"]
}
```

Measured on TypeScript 7.0.2, on a scratch copy of the folder with `.js` dropped from the `tools` import. **The config above, unchanged:**

```
$ npx tsc --noEmit -p tsconfig.json
server.ts(23,60): error TS2835: Relative import paths need explicit file extensions in
ECMAScript imports when '--moduleResolution' is 'node16' or 'nodenext'. Did you mean './tools.js'?
```

**The same code, under an ordinary bundler-style config** — `"module": "esnext"` with `"moduleResolution": "bundler"`, everything else identical:

```
$ npx tsc --noEmit -p tsconfig.json
(no output)
```

**That second one is the trap**, and it is worth being precise about its shape, because the near-miss behaves in the opposite way. A *self-consistent* bundler config is a perfectly reasonable thing to write, and under it everything passes: `TS2835` never fires, the import is left in a form Node will not resolve, and the only check that was going to catch it has been switched off by the file that was supposed to run it.

Changing **only** `moduleResolution` and leaving `module` at `nodenext` is not that case — it fails, immediately and loudly, before compiling anything:

```
tsconfig.json(4,25): error TS5095: Option 'bundler' can only be used when 'module' is set to
'preserve', 'commonjs', or 'es2015' or later.
tsconfig.json(4,25): error TS5109: Option 'moduleResolution' must be set to 'NodeNext' (or left
unspecified) when option 'module' is set to 'NodeNext'.
```

So the half-change is safe — it stops you and names the conflict. **The dangerous edit is the coherent one**, where both keys move together and nothing complains. That is the shape to watch for when someone regenerates this file or copies a `tsconfig.json` in from another project.

`strict` matters for the same reason: the heterogeneous-array error at `:290` only appears under it, so dropping it also removes a check without removing anything visible.

## Where the credential is kept

`credentials.md` obtains and proves the credential and hands it here. It lives in **`agent-access/.env`**, and:

- **`.env` is in `agent-access/.gitignore`, alongside `calls.log` and `node_modules/`.** The folder carries its own `.gitignore` rather than relying on the repository's, because the repository's is a file the owner wrote and this skill does not edit files the owner wrote.
- **`.env.example` is committed and holds the key names with empty values**, so the next person can see what is required without the secret being in the history.
- **It is read once, at module scope, into a `const`.** It is never a tool parameter and never part of a tool's return value.
- **It is never logged.** The log line carries the tool name, the arguments the tool was given, and the outcome — see the rule below.
- **It is loaded by absolute path**, because the process's working directory is the client's choice. Measured with the server started from another directory, a bare `config()` returns `ENOENT` and leaves `APP_API_TOKEN` undefined — printing nothing either way.

**A missing credential must stop the server, not degrade it.** With no start-up check the header goes out as the literal string `Token undefined`, and DRF answers:

```
$ curl -s -H "Authorization: Token undefined" http://127.0.0.1:8003/api/orders/
{"detail":"Invalid token."}
```

Read against `credentials.md`, "Invalid token" means *the scheme word is right and the value is wrong* — so the next hour goes on rotating a token that was never the problem. The `throw` at the top of `tools.ts` costs three lines and names the cause instead.

**Revocation must be one command, and it must be tested rather than described.** Deleting the token row was actually run against the fixture, with the server still registered and the app still up:

```
$ python manage.py shell -c "
  from rest_framework.authtoken.models import Token
  Token.objects.filter(user__username='agent').delete()"
deleted rows: 1
```

The next tool call, through the client, with nothing else changed:

```
The app returned HTTP 401: {"detail":"Invalid token."}
```

and in the log:

```
{"at":"2026-08-16T18:47:29.153Z","tool":"list_orders","args":{"limit":2},"outcome":"error http_401"}
```

Immediately, with no restart, and no person logged out of anything — which is the whole argument for the dedicated `agent` user. To rotate rather than revoke, create the token again and put the new key in `.env`; the fixture's key above is the second one, because this test was run.

Put that command in the generated `README.md`. An owner who cannot switch a thing off in one line does not really control it.

## The rules that apply to every generated server

### Writes go through the app's API. Always.

No SQL write, no exception, no flag. `credentials.md` gives the reason and makes the database user incapable of it: an agent writing SQL skips the app's validation, permissions, hooks and audit logging, and leaves the app in a state its own code believes impossible. That surfaces later, somewhere unrelated, as a bug nobody can reproduce.

If the app has no API, there are no write tools. `discovery.md`'s no-API section is the branch to take, and it has to be taken at interview step 2 — as soon as discovery answers the question, and before the capability list at step 3 is agreed. Step 1 is too early to know: it settles which app, not what is in it.

### Every list tool takes `limit`, capped in the schema **and** where the rows are handled

An uncapped list either truncates mid-JSON into something the client cannot parse, or hands one call the entire account.

**The schema cap.** `z.number().int().min(1).max(MAX_LIMIT).default(20)` becomes `"maximum": 50` in the advertised JSON schema, and the SDK rejects an over-large argument before the handler runs. Measured, asking a real client for 500:

```
MCP error -32602: Input validation error: Invalid arguments for tool list_orders:
Too big: expected number to be <=50 at limit
```

**The second cap, where the rows arrive, is not belt-and-braces.** It is the one doing the work, because **the app is free to ignore the limit you send it**. DRF's unpaginated list view accepts unknown query parameters and returns everything, with a 200 and no warning. Measured against 60 rows:

```
$ curl -s -H "Authorization: Token $K" "http://127.0.0.1:8003/api/orders/?limit=50" \
    | python -c "import sys,json; print('rows returned by the app:', len(json.load(sys.stdin)))"
rows returned by the app: 60
```

The same call through the tool returned **50**, and said so:

```
{"at":"2026-08-16T18:28:10.928Z","tool":"list_orders","args":{"limit":50},"outcome":"ok 50 of 60 rows"}
```

`?page_size=50` was measured too and is ignored the same way. **So send the cap and then apply it again to what comes back**, and log both numbers — `50 of 60` is the line that tells a reader the app is not paginating and the server is.

**Say what this second cap does not do**, because it is easy to read it as more than it is. It truncates *after* `res.json()` has parsed the whole payload, so an app that ignores `limit` still transfers and deserialises every row before fifty are kept. It bounds what the assistant is handed — the failure the rule exists to prevent — and it does not bound what the process holds on the way there. On a table with a million rows the tool result is fine and the memory is not. Where that matters, the fix is upstream: get the app to paginate, or use the SQL variant below, where `LIMIT` is enforced by the database and only `capped` rows are ever built.

Where a read goes to SQL instead, the cap is a bound `LIMIT` in the statement — see the database variant below.

### No delete tool, in any generated server

Not "unless the owner asks". `django_api`'s router serves `DELETE /api/orders/<pk>/` and it is enumerated in the route list; the generated server exposes three tools and none of them is delete. Throwing work away is a decision for a person, in the app, where they can see what they are throwing away.

A tool that deletes is also the one whose mistakes cannot be inspected afterwards. Every other wrong call leaves a row to look at.

### Log every call, with the tool name, the arguments and the outcome

To `agent-access/calls.log`, one JSON line per call, opened by absolute path for the same reason `.env` is. The write cycle from the verification run, read straight out of the file — a write, the read-back that confirmed it, and the same read after the row was deleted in the admin:

```
{"at":"2026-08-16T18:48:05.965Z","tool":"list_orders","args":{"limit":2},"outcome":"ok 2 of 3 rows"}
{"at":"2026-08-16T18:49:32.371Z","tool":"create_order","args":{"customer":"Grace Hopper","total":"412.00"},"outcome":"ok created id=5"}
{"at":"2026-08-16T18:49:34.365Z","tool":"get_order","args":{"id":5},"outcome":"ok"}
{"at":"2026-08-16T18:50:56.214Z","tool":"get_order","args":{"id":5},"outcome":"error http_404"}
```

Four lines, and between the third and the fourth a person opened the Django admin and deleted the row. The log does not know that happened — it records what the assistant asked for, and the 404 is the shadow the deletion casts. That is the right division: the app's own audit trail records what the app did; this file records what was asked of it.

Without it, "what did it do?" is answerable only from the assistant's own account of what it did, which is the one source that cannot be checked. The log is also how a write gets traced back to the call that made it, weeks later, by someone who was not there.

**One thing the log cannot tell you, and it is worth knowing before you rely on it:** a call rejected by the schema never reaches the handler, so it writes no line. The `limit: 500` attempt above appears nowhere in the file. The log records what the app was asked to do, not every message the client sent.

Log the arguments, never the headers. Arguments are the caller's; headers carry the credential.

### Secrets never leave a tool — destructure, never spread

Return an object built field by field. Never `...row`, never `{ ...record, extra }`.

This one was measured rather than assumed. A column was added to `django_api`'s `Order` model and the app's serialiser left at DRF's very common `fields = "__all__"`. The app's API immediately began returning it:

```
$ curl -s -H "Authorization: Token $K" http://127.0.0.1:8003/api/orders/1/
{"id":1,"customer":"Ada","total":"9.99","created_at":"2026-08-16T18:22:27.196368Z",
 "internal_note":"FLAGGED FOR FRAUD REVIEW"}
```

The same row through `get_order`, with no change to `agent-access/`:

```json
{
  "id": 1,
  "customer": "Ada",
  "total": "9.99",
  "created_at": "2026-08-16T18:22:27.196368Z"
}
```

`shapeOrder` dropped it because it lists the four fields it knows about. A spread would have forwarded it the day the column was added — and nothing would have failed, nothing would have warned, and no file in `agent-access/` would have changed to record that the assistant's view of the app had widened. That is the failure: not a leak that breaks something, a leak that works perfectly.

(The column and the widened serialiser were reverted afterwards; the fixture is back to four fields.)

### Read tools get `readOnlyHint`, writes get `destructiveHint: false`

```ts
annotations: { readOnlyHint: true }                                            // reads
annotations: { readOnlyHint: false, destructiveHint: false, idempotentHint: false }  // writes
```

They are advertised in `tools/list` — confirmed in the fixture's own output, `"annotations":{"readOnlyHint":true}` — and they are how a client tells a read apart from a write without reading the code. What each client does with that is the client's business and is not something this file can promise; what this file can promise is that the annotation is present and true.

`destructiveHint: false` says this write adds something rather than replacing or removing something. It is a true statement about `create_order` and it would be a false one on an update tool, and a false annotation is worse than none — it is the one the client trusts.

### stdout belongs to the protocol

Every diagnostic goes to `console.error`. A stray `console.log` puts a non-JSON-RPC line into the message stream, and what the client then reports is a parse error naming the transport rather than the line that printed it. The start-up line in `server.ts` is on stderr for exactly this reason, and it appeared there on every run, interleaved with nothing:

```
agent-access: 3 tools, stdio
{"result":{"protocolVersion":"2024-11-05", ... },"jsonrpc":"2.0","id":1}
```

### Use the URL discovery proved, character for character

The trailing slash is not cosmetic, and on a write it is not even a redirect. Measured on `django_api`:

```
GET  /api/orders   -> 301
GET  /api/orders/  -> 200
POST /api/orders   -> 500
```

That 500 is Django's `APPEND_SLASH` refusing to lose the body, raised as a `RuntimeError`:

```
You called this URL via POST, but the URL doesn't end in a slash and you have
APPEND_SLASH set. Django can't redirect to the slash URL while maintaining POST data.
```

(Read off the debug page, with `DEBUG = True`. On a deployment with debug off the same fault is a bare 500 and the sentence is only in the server's own log — so on someone else's production app, expect the status and not the explanation.)

So a write to the slashless URL fails as a **server error**, which reads as the app being broken rather than the client being one character wrong. `redirect: "error"` on the fetch does not catch it, because nothing redirected — measured, it did not throw. Note also that `/api/orders.json` returns **200** on this app's `ModelViewSet` while the same route returns **500** on `django_shop`'s plain `ViewSet`. Two DRF apps, opposite answers: probe this app, never carry a result across from another.

## Variant: writing through a session cookie and CSRF

**Not exercised in this verification run.** `django_api` has a token path and `credentials.md` says to prefer it where one exists, so the worked example above uses `Authorization: Token`. The CSRF evidence below is carried over from `credentials.md`, which measured it against `django_html` on the same day. **Treat the shape as sound and the code as unrun.**

Where the app has no token path, a write needs three things together on every unsafe request: the `sessionid` cookie, the `csrftoken` cookie, and the same CSRF value in an `X-CSRFToken` header — plus a same-origin `Referer`, which Django only enforces over HTTPS and which therefore starts failing when the integration is pointed at production.

```ts
// Variant, for a session-authenticated app. Fetch the CSRF token once at
// start-up from any page that sets the cookie, and send it on every write.
const jar = new Map<string, string>();

function cookieHeader() {
  return [...jar].map(([k, v]) => `${k}=${v}`).join("; ");
}

async function write(path: string, form: Record<string, string>) {
  return fetch(`${BASE_URL}${path}`, {
    method: "POST",
    headers: {
      Cookie: cookieHeader(),
      "X-CSRFToken": jar.get("csrftoken") ?? "",
      Referer: `${BASE_URL}${path}`,       // same origin; only checked over HTTPS
      "Content-Type": "application/x-www-form-urlencoded",
    },
    body: new URLSearchParams(form).toString(),
    redirect: "manual",                    // a successful Django form POST is a 302
  });
}
```

Three things about it that cost an hour each, all from `credentials.md`:

- **A 200 from a form POST is a failure.** Django re-renders the form with validation errors inside a 200. Check for the 302, which is why `redirect: "manual"` is there — following it turns the evidence of success into the page you land on.
- **Cookie and header must both be present.** One is no better than neither, and the 403's reason line is the only thing that says which is missing.
- **Never exempt a route from CSRF to make this work.** It is a real security regression in somebody else's app, arrived at by accident, and it outlives the demo.

## Variant: reading from the database, where there is no API for it

Only where `discovery.md` found no route for that read, and only with the read-only credential `credentials.md` created and proved. **Reads only. No generated tool changes a row over SQL.**

**Open it with `node:sqlite`, built into Node 22 and later.** No dependency, so nothing is added to `package.json`:

```ts
import { DatabaseSync } from "node:sqlite";

const db = new DatabaseSync(DB_PATH, { readOnly: true });
```

**`readOnly` — capital O.** This is the whole reason the driver is named here rather than left to the generator, and it was measured, three ways, against a copy of the fixture's database:

```
node:sqlite { readOnly: true }  (correct)   -> INSERT refused: attempt to write a readonly database
   rows before/after: 3 3
node:sqlite { readonly: true }  (near-miss) -> INSERT COMMITTED  <-- writable handle
   rows before/after: 3 4
node:sqlite {}                  (no option) -> INSERT COMMITTED  <-- writable handle
   rows before/after: 4 5
```

**The lowercase spelling does not throw and does not warn.** It is an unrecognised property on an options object, so it is ignored in silence, and what comes back is an ordinary read-write handle that looks exactly like the safe one.

**And the other obvious driver spells it the other way round — and, unlike this one, says so.** `better-sqlite3` takes lowercase `readonly`, and it checks for the mistake explicitly. Measured, same database, same probe:

```
better-sqlite3 { readonly: true }  (its spelling) -> refused: attempt to write a readonly database
better-sqlite3 { readOnly: true }  (node's)       -> TypeError: Misspelled option "readOnly" should be "readonly"
```

So the two libraries are not merely inconsistent, they are **asymmetric in the direction that matters**: get it wrong on `better-sqlite3` and the process stops with a message naming the correct spelling; get it wrong on `node:sqlite` and you are handed a writable database and told nothing. Someone who learned the habit on the safe one carries it to the unsafe one and never finds out. That asymmetry is why the driver is named here rather than left to the generator — and why the check below is not optional even when the option looks right.

**So prove it after opening, every time, whatever the driver.** One statement at start-up:

```ts
// A write statement that matches no rows: refused outright on a read-only
// handle, and a no-op on a writable one. Never use an INSERT here - on the
// failing branch it would perform the write it exists to forbid.
const NOOP_WRITE = "UPDATE orders_order SET customer = customer WHERE 1 = 0";

let refused = false;
try {
  db.prepare(NOOP_WRITE).run();
} catch (e) {
  refused = /readonly database/i.test(String(e));
  if (!refused) throw e;              // some other fault - do not swallow it
}
if (!refused) {
  throw new Error(
    "This handle accepted a write. Refusing to start: the read-only option was not " +
      "honoured - check its spelling. Nothing was changed.",
  );
}
```

Measured, the same three ways, and note the last column:

```
{ readOnly: true }  (correct)   -> refused: attempt to write a readonly database
      rows/sum before: 3 136.49  after: 3 136.49
{ readonly: true }  (near-miss) -> WRITABLE (no refusal)
      rows/sum before: 3 136.49  after: 3 136.49
{}                  (no option) -> WRITABLE (no refusal)
      rows/sum before: 3 136.49  after: 3 136.49
```

It separates the three cases correctly **and changes nothing in any of them** — same row count, same total, before and after, on all three handles. That is the property that makes it usable as a start-up check: the probe cannot itself become the accident. It is also driver-independent — the same statement is refused with the same message by `better-sqlite3` opened `{ readonly: true }`, so nothing above has to be rewritten if the driver changes.

Two other probes were tried and rejected on measurement. An `INSERT` separates the cases, but on the writable handles it **commits the row** — it performs the write it exists to prevent, which is how the fixture copy went from 3 rows to 5 while this was being worked out. And `BEGIN IMMEDIATE` changes nothing but **does not separate the cases at all**: SQLite defers acquiring the write lock, so it succeeded on the genuinely read-only handle too, and reported all three as writable. A probe that says "writable" for a safe connection fails closed, which is survivable; the point is that it proves nothing.

Not "it is configured read-only" — **"a write was attempted and refused, on this handle, on this run"**. An option that was ignored passes every other check you can write.

And a refusal here is still only evidence about the *connection*. `credentials.md`'s SQLite section is the authority on the rest and does not soften: a read-only mode chosen by the connecting code can be unchosen by the connecting code, so on SQLite the file permissions are doing the work and the owner must be told so in those words. On Postgres or MySQL the same probe is evidence about the *database*, because the permission lives there and the connection cannot grant itself one — which is why `credentials.md` creates `agent_readonly` rather than trusting a flag.

Two smaller things from the same run: `node:sqlite` prints `ExperimentalWarning: SQLite is an experimental feature` on **stderr**, which is harmless here for the reason given above — stdout is the protocol and stderr is not. And the cap is a bound `LIMIT` in the statement, applied before it is built:

```ts
const capped = Math.min(limit, MAX_LIMIT);
const rows = db.prepare(
  "SELECT id, customer, total, created_at FROM orders_order ORDER BY id DESC LIMIT ?"
).all(capped);
```

That form has an advantage the HTTP version does not: the database returns `capped` rows, so nothing oversized is ever built in memory.

**Note what the same row looks like down the two paths**, because this is the trap in mixing them. The API returned `"total":"102.00"` and `"created_at":"2026-08-16T18:22:27.234439Z"`. The database returned `"total":102` — a JavaScript number, the trailing zeroes and the decimal type gone — and a timestamp in a different format with no timezone marker. Same row, same instant, two shapes. An assistant comparing a figure from a SQL-backed tool against one from an API-backed tool is comparing two different things, and nothing in either result says so. **Where both paths exist for the same data, use the API for both.**

## The generated `README.md`

It is written for whoever finds this folder in six months and does not know what it is. It records what was built, how it reaches the app, and — the part that is easy to leave out — what the owner agreed to.

The generated file for `django_api`:

```markdown
# Agent access for django_api

Generated on 2026-08-16 by the `bring-your-own-agent` skill.

Everything in this folder was added by the skill. **No file outside this folder
was changed.** Delete the folder and the app is exactly as it was.

## What this lets an assistant do

| Tool | What it does | How it reaches the app |
|---|---|---|
| `list_orders` | Lists recent orders, newest first, at most 50 | `GET /api/orders/` |
| `get_order` | One order by id | `GET /api/orders/{id}/` |
| `create_order` | Creates an order | `POST /api/orders/` |

**Every tool goes through the app's own API.** No tool touches the database
directly, so the app's validation, permissions and any rules in its own code
apply to everything the assistant does — exactly as they would to a person
using the app.

**There is no delete tool.** `DELETE /api/orders/{id}/` exists in the app and is
deliberately not exposed here. Deleting is done by a person, in the app, where
they can see what they are deleting.

## The one thing to understand before using it

> This assistant acts as one fixed login — the `agent` user. Anything that login
> can see or change, the assistant can see or change too. There is no per-person
> permission screen, and no way to give one person less access than another.

To switch it off entirely, delete that user's token:

    python manage.py shell -c "
    from rest_framework.authtoken.models import Token
    Token.objects.filter(user__username='agent').delete()
    "

Every tool starts failing immediately. Nobody else is logged out, because the
`agent` user is not a person's account.

## Why this rather than building it into the app

Building agent access inside django_api itself was offered and **declined in
favour of this** on 2026-08-16. In the app it would have had access to each
user's own session and permissions; out here it is one fixed identity, which is
the trade that was made knowingly. It is written down so a later reader knows
it was a choice and not an oversight.

## Running it

    cd agent-access
    npm install
    cp .env.example .env      # then fill in APP_API_TOKEN

Register it with a client that speaks MCP over stdio:

    claude mcp add django-api-agent-access -- \
      node <abs>/agent-access/node_modules/tsx/dist/cli.mjs <abs>/agent-access/server.ts

Use absolute paths. The client chooses the working directory this process starts
in, and it is not this folder.

The app must be running: `python manage.py runserver 127.0.0.1:8003`.

## The credential

`APP_API_TOKEN` is a DRF token for the `agent` user. It lives in
`agent-access/.env`, which `agent-access/.gitignore` keeps out of the
repository. It is never returned by a tool and never written to the log.

To rotate it, delete the token row as above and create a new one, then update
`.env`. The old key stops working the moment the row is deleted.

## What it did

Every call appends one JSON line to `agent-access/calls.log` — the time, the
tool, the arguments it was given, and how it went:

    {"at":"2026-08-16T18:48:05.965Z","tool":"list_orders","args":{"limit":2},"outcome":"ok 2 of 3 rows"}

The log is gitignored, holds no credential, and is the record of what the
assistant actually did. Read it before believing any account of what happened.
```

That is the whole file, not an outline — a generated README with an ellipsis in it is a README nobody finished.

Six things must be in it, and the last is the one that gets dropped:

1. **Which path each tool uses** — API or database, per tool, in a table.
2. **Whether the database fallback is in play at all.** If it is, `credentials.md`'s row-visibility disclosure goes here too: the assistant can see rows the app would normally hide, because filters written in the app's code are invisible to the database.
3. **That the agent acts as one identity**, in the words `credentials.md` gives.
4. **How to run it** — install, the `.env` step, and the exact registration command with absolute paths — plus that the app itself has to be up. Whoever finds this folder in six months has to be able to start it without reading the source.
5. **How to switch it off**, in one command, with what happens when you do.
6. **That the in-app alternative was offered and the owner chose this**, with the date. Without that line, the next reader finds a folder full of workarounds and assumes nobody knew better. With it, they know the trade was made deliberately and can weigh it again on its merits.
