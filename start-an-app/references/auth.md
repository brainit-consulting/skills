# Sign-in (Better Auth)

Last verified: 2026-09-21

**Purpose:** User accounts with Better Auth on top of the existing Drizzle database. Default is email + password (works with zero external setup). Google sign-in is an optional add-on with a guided walkthrough.

**Which access shape is this app?** The interview settled one of four, and every file uses these names: **open sign-up** (anyone can create an account), **one owner** (sign-up closes after the first account), **invited people only** (the owner invites; strangers cannot sign up), or **no accounts** (skip this file). A public site with one author is "one owner" with a public front. The shape decides which version of the hook below goes in.

> **Do not create an account while building this step.** The first account on any database becomes the admin, and on a one-owner app it takes the only seat and locks the person out of their own app. The first account is the real person's, made in Step 6. Everything in Verify that needs a signed-in account is deferred to then.

> Compatibility note (the one fragile pairing in this stack): the Better Auth ↔ Drizzle adapter's table schema is generated by the Better Auth CLI. Always generate it with the CLI rather than hand-writing the tables, and re-run generation after upgrading `better-auth`. The CLI is the npm package `auth`. The older `@better-auth/cli` package is frozen and marked unsupported; it still installs, which is how a project ends up generating a schema for a release it is not running.

## Install

```bash
pnpm add better-auth
```

Append to `.env` (generate the secret with `openssl rand -base64 32`):

```
BETTER_AUTH_SECRET=<generated>
BETTER_AUTH_URL=http://localhost:3000
```

**`BETTER_AUTH_URL` must match the port the dev server actually got.** Next.js takes 3001, 3002, 3003… when 3000 is busy, and Better Auth checks the request origin against this value: if they disagree, every sign-up and sign-in fails with **`Invalid origin`** — a message that says nothing about ports and sends people hunting through their database and cookie settings instead.

So read the port off the dev server's own output rather than assuming, write that value, and **restart the dev server** — `.env` is read at boot, so editing it while the server runs changes nothing and looks like the fix didn't work. If sign-in ever starts returning `Invalid origin` later, this is why: the port moved.

## Configure

`src/lib/auth.ts` — use `provider: "sqlite"` or `provider: "pg"` to match the database branch:

```ts
import { betterAuth } from "better-auth";
import { drizzleAdapter } from "better-auth/adapters/drizzle";
import { nextCookies } from "better-auth/next-js";
import { db } from "@/lib/db";

export const auth = betterAuth({
  baseURL: process.env.BETTER_AUTH_URL,
  database: drizzleAdapter(db, { provider: "sqlite" }),
  emailAndPassword: { enabled: true },
  user: {
    additionalFields: {
      role: {
        type: ["user", "admin"],
        required: false,
        defaultValue: "user",
        input: false, // the security control: without it a user can set their own role
      },
    },
  },
  // databaseHooks: the first-account hook from "The role field and the first account" below
  plugins: [
    nextCookies(), // must stay last in the list
  ],
});
```

`nextCookies` comes from `better-auth/next-js`. Without it, a sign-in performed inside a server action never sets its cookie. Any plugin added later goes above it. The adapter import `better-auth/adapters/drizzle` is the supported path and is not deprecated. Use it as written.

The `role` field goes in **now, before the first generate**, so the column exists from the first migration. Measured on a real build: with the field added only at settings time, the first-account hook spent twelve steps setting a column that did not exist.

Generate the auth tables into the Drizzle schema, then migrate:

```bash
pnpm dlx auth@latest generate --config src/lib/auth.ts --output src/lib/db/auth-schema.ts -y
pnpm db:generate
pnpm db:migrate
```

(Two different "generate" steps, easy to confuse: the Better Auth CLI writes the Drizzle *table definitions*, then `db:generate` turns those into a *SQL migration*. Never `drizzle-kit push` — see `references/database.md`.)

Open the generated `auth-schema.ts` and the new migration and confirm the `user` table has a `role` column before going on. Any later change to `additionalFields` (wider role values, a profile field) means running the same three commands again.

**Noise to expect, and ignore:** the CLI prints a `Drizzle schema mismatch ... Missing tables` error and then succeeds (seen on two builds; the tables are missing because this is the run that creates them). pnpm may also print an unmet `zod` peer warning and an "Ignored build scripts" notice. None of the three stops anything.

**Three things make the first run fail, none of them with a useful message:**

- `src/lib/db/schema.ts` re-exports `./auth-schema`, and `auth.ts` loads the database module, so the file the CLI is about to write has to exist already. Create a placeholder first — `export const user = pgTable("user", { id: text("id").primaryKey() });`, or the same line with `sqliteTable` on the SQLite branch — and let the CLI overwrite it.
- The CLI loads `auth.ts` outside Next.js. Anything in that import chain that imports `"server-only"` stops it with `Cannot find module 'server-only'`. That means the database module, the email helper, the email templates, and anything else `auth.ts` reaches. Keep `server-only` for pages, actions and libraries that only Next.js ever imports. The same applies to any file a `tsx` script imports, such as a seed script.
- If the CLI cannot resolve one `@/…` import in `auth.ts`, switch that import to a relative path and leave the rest.

Re-export the generated tables from `src/lib/db/schema.ts` (`export * from "./auth-schema";`) so Drizzle sees them.

Leave `auth-schema.ts` exactly as generated — don't "tidy" its columns or switch its `text` ids to UUIDs to match your own tables. Your tables use UUID ids, but a column referencing `user.id` stays `text` in both database branches; `references/database.md` has the rule and the examples.

API route `src/app/api/auth/[...all]/route.ts`:

```ts
import { auth } from "@/lib/auth";
import { toNextJsHandler } from "better-auth/next-js";

export const { GET, POST } = toNextJsHandler(auth);
```

Client helper `src/lib/auth-client.ts`:

```ts
import { createAuthClient } from "better-auth/react";

export const authClient = createAuthClient();
export const { signIn, signUp, signOut, useSession } = authClient;
```

Build simple `/sign-in` and `/sign-up` pages with shadcn form components using `signIn.email` / `signUp.email`, and show the signed-in user (with a sign-out button) in the app's header via `useSession`. These pages and the header follow `DESIGN.md`, which already exists because the design step runs before this one: use its tokens and type, not stock greys.

**No email verification or password reset yet, and that's deliberate.** Better Auth can do both, but neither exists until there is somewhere to send the message from. If the user chose email, `references/email.md` wires them up; if they didn't, sign-in works exactly as configured above and reset can be added later without touching anything here.

When reset is wired up, the client side is `authClient.requestPasswordReset({ email, redirectTo })` followed by `authClient.resetPassword({ newPassword, token })`.
`references/settings.md` later adds `session.freshAge`, `changeEmail`, `deleteUser` and rate limits to this file. The `role` field and the first-account hook are already here by then; it does not add them again.

## The role field and the first account

Someone has to be able to see the system page, and asking the person to hand-edit a database row is a bad first experience. So the first account created becomes the admin. What happens to every account after that depends on the access shape, and it is **one hook with three versions, not three hooks**.

Ask of every app: can a stranger create an account? For a product people sign up for, yes. For a tool with one owner, or a team tool, leaving `/sign-up` open is a hole, and the interview usually implies the answer without anyone saying it.

`emailAndPassword.disableSignUp` is a fixed setting, so it cannot mean "open for the first person, closed afterwards". A database hook can, and it covers any sign-in method added later. Add these imports to `src/lib/auth.ts`:

```ts
import { APIError } from "better-auth/api"; // not needed for open sign-up
import { count } from "drizzle-orm";
import { user as userTable } from "./db/auth-schema"; // relative on purpose: the Better Auth CLI cannot resolve the alias here
```

Then add the version that matches the access shape to the `betterAuth` config.

**Open sign-up** — the first account is the admin, everyone after is a user:

```ts
databaseHooks: {
  user: {
    create: {
      before: async (user) => {
        const [row] = await db.select({ n: count() }).from(userTable);
        return { data: { ...user, role: row.n === 0 ? "admin" : "user" } };
      },
    },
  },
},
```

**One owner** — the first account is the admin, and any later create is refused:

```ts
databaseHooks: {
  user: {
    create: {
      before: async (user) => {
        const [row] = await db.select({ n: count() }).from(userTable);
        if (row.n > 0) {
          throw new APIError("FORBIDDEN", { message: "This app already has an owner. Sign-up is closed." });
        }
        return { data: { ...user, role: "admin" } };
      },
    },
  },
},
```

Measured on a real build: with one account in place, a second `POST` to `/api/auth/sign-up/email` answered `403` and the user count did not change.

**Invited people only** — the first account is the admin; a later create is allowed only when the email has a pending invitation, and the role comes from the invitation, never from the form. The hook and the table it reads are in *More than two roles, and invitations* below.

Two accounts created in the same instant could both come out as admin. For a new app with one owner that is not worth solving; if the user asks, the answer is a unique partial index or seeding the role deliberately. Mention it only if they ask.

The `/sign-up` page does the same count on the server and shows a sentence instead of a form once it is closed. For invited-people-only apps it never shows a form: the way in is the invitation link.

**Do not test the closed door by signing up.** The refusal can only be seen once a first account exists, and that account must be the real person's. The check is in Verify, deferred to Step 6.

## More than two roles, and invitations

> **Not yet built with this skill.** Everything in this section is a design, written from a desk-check of a team tool with three roles. Confirm the Better Auth API it names (`auth.api.signUpEmail`, `databaseHooks`, the `additionalFields` type list) in the check-what's-current step, and prove it with the Verify items below. Do not tell the user any of it works until those have been run.

Use this section when the interview named real roles ("the owner, the office, the plumbers") or when the access shape is invited people only. An open sign-up or one-owner app with just "admin and everyone else" does not need it.

**Roles.** Keep the role names in one small file that imports nothing from Next, because `auth.ts` reads it and the CLI loads `auth.ts` outside Next:

```ts
// src/lib/roles.ts
export const ROLES = ["owner", "office", "plumber"] as const; // this app's real roles, from the build sheet
export type Role = (typeof ROLES)[number];

/** The one role that may open the system page. requireAdmin() checks for this. */
export const ADMIN_ROLE: Role = "owner";

/** What an invited person gets when nothing else is said. Never the admin role. */
export const DEFAULT_ROLE: Role = "plumber";
```

In `src/lib/auth.ts`, widen the field to those values (`type: [...ROLES]`, `defaultValue: DEFAULT_ROLE`, `input: false` stays) and have the hook give the first account `ADMIN_ROLE` instead of `"admin"`. Then run the three generate-and-migrate commands again. Wherever another file says `role === "admin"`, this app says `role === ADMIN_ROLE`.

**The invitation table** is the app's own, so it follows `references/database.md` (UUID id, and the column pointing at a user stays `text`). Postgres shown; the SQLite branch uses its own column helpers:

```ts
export const invitation = pgTable("invitation", {
  id: uuid("id").primaryKey().defaultRandom(),
  email: text("email").notNull(), // stored lower-cased
  role: text("role").notNull(), // one of ROLES, checked in the invite function
  token: text("token").notNull().unique(), // long and random; it is the whole key to the accept page
  invitedBy: text("invited_by").references(() => user.id, { onDelete: "set null" }),
  expiresAt: timestamp("expires_at", { withTimezone: true }).notNull(),
  acceptedAt: timestamp("accepted_at", { withTimezone: true }),
});
```

`invitedBy` uses `set null`, not `cascade`: an admin who leaves must not take the team's pending invitations with them.

**The hook, invited-people-only version:**

```ts
import { and, count, eq, gt, isNull } from "drizzle-orm";
import { invitation } from "./db/schema"; // relative, for the same reason as auth-schema
import { ADMIN_ROLE } from "./roles";

databaseHooks: {
  user: {
    create: {
      before: async (user) => {
        const [row] = await db.select({ n: count() }).from(userTable);
        if (row.n === 0) return { data: { ...user, role: ADMIN_ROLE } };

        const [invite] = await db
          .select()
          .from(invitation)
          .where(
            and(
              eq(invitation.email, user.email.toLowerCase()),
              isNull(invitation.acceptedAt),
              gt(invitation.expiresAt, new Date()),
            ),
          )
          .limit(1);
        if (!invite) {
          throw new APIError("FORBIDDEN", { message: "This app is invite-only. Ask the owner for an invitation." });
        }
        return { data: { ...user, role: invite.role } };
      },
    },
  },
},
```

Because the check is in the hook, it holds for every way an account can be created, including a direct `POST` to `/api/auth/sign-up/email` and any social sign-in added later.

**Inviting.** One server action, `inviteMember(email, role)`, in the admin area: it calls `requireAdminAction()`, checks the role is one of `ROLES`, writes the invitation row with a random token and an expiry (seven days is a reasonable default), and sends the link `${baseUrl}/invite/${token}` (where `baseUrl` is `process.env.APP_URL || process.env.BETTER_AUTH_URL || "http://localhost:3000"`, with `||` so an empty value cannot win; use `siteUrl` from `src/lib/site.ts` once `references/seo.md` has written it) through `sendEmail` from `references/email.md`. If the app has no email, the action returns the link and the page shows it with a copy button so the owner can pass it on themselves. Keep the writing part in a shared `src/lib/<domain>` function so `references/verify.md` can create its fixtures through the same code from a script.

**Accepting.** `src/app/invite/[token]/page.tsx`, outside the protected group. On the server it looks the token up; an unknown, used or expired token gets one plain sentence and no form. Otherwise it shows the invited email as fixed text and asks for a name and a password. The form's server action looks the token up again, calls `auth.api.signUpEmail({ body: { email: invite.email, name, password }, headers: await headers() })` with the email taken **from the invitation row, not from the form**, and then sets `acceptedAt`. `nextCookies()` is what lets that server-side call set the session cookie, so the person lands signed in.

**Guards, and when to build this.** `references/pages.md` writes `requireUser()` and `requireUserAction()` in `src/lib/auth-guards.ts`, and `references/settings.md` adds `requireAdmin()` and `requireAdminAction()`. Neither file has run when sign-in is built. So at this step build only what needs no guard: the roles file, the invitation table, the hook variant and the accept page. The invite action, the role-change function and the role guard below are written after `references/settings.md` has run, when the guards they call exist. Then add a role guard beside the others:

```ts
import { notFound } from "next/navigation";
import type { Role } from "@/lib/roles";

/** For pages: a signed-in person with the wrong role sees a 404, not an error page. */
export async function requireRole(...roles: Role[]) {
  const session = await requireUser();
  if (!roles.includes(session.user.role as Role)) notFound();
  return session;
}

/** For server actions and route handlers: throws instead. */
export async function requireRoleAction(...roles: Role[]) {
  const session = await requireUserAction();
  if (!roles.includes(session.user.role as Role)) throw new Error("Not allowed");
  return session;
}
```

A guard on a page is not the data rule. For records a team shares, every query in the shared `src/lib/<domain>` functions is scoped by role (a plumber gets the jobs assigned to them; the office gets all of them), as `references/pages.md` and `references/database.md` describe.

**Changing someone's role.** `input: false` means `authClient.updateUser` cannot touch the field, which is the point. So the change is a server function that calls `requireAdminAction()` first and then updates the `role` column with Drizzle. **This is the one allowed exception to "never write the `user` table directly"**: `role` is the app's own field, Better Auth stores it and otherwise ignores it, and no session, token or password hash depends on it. Nothing else on that table is written this way. Two refusals belong in the function: an admin cannot change their own role, and the last account holding `ADMIN_ROLE` cannot be demoted, or the app ends up with nobody who can open the system page.

**Removing a member** is a different thing from changing a role, and `references/settings.md` covers what it must not delete.

## Google sign-in (optional add-on)

Walk the user through it — plain language, one step at a time:

1. Open https://console.cloud.google.com/ and create a project (any name).
2. Go to **APIs & Services → OAuth consent screen**, choose External, fill in just the app name and your email.
3. Go to **APIs & Services → Credentials → Create Credentials → OAuth client ID**, type **Web application**.
4. Add authorized redirect URI: `http://localhost:<the port the dev server actually got>/api/auth/callback/google` — the same port as `BETTER_AUTH_URL` above, not 3000 by assumption. Google matches the redirect URI **exactly, including the port**, so a dev server that moved to 3001 fails with `redirect_uri_mismatch` and nothing in that message mentions ports. Add a second URI for each port they realistically use rather than editing it every time.
5. Copy the Client ID and Client Secret into `.env`:

```
GOOGLE_CLIENT_ID=<from console>
GOOGLE_CLIENT_SECRET=<from console>
```

Extend the `betterAuth` config. The provider is included only when both values are present, so a missing or blank key means no Google button rather than a crash, and there are no non-null assertions for `references/verify.md` to find:

```ts
const googleClientId = process.env.GOOGLE_CLIENT_ID;
const googleClientSecret = process.env.GOOGLE_CLIENT_SECRET;

// inside betterAuth({ ... })
socialProviders: {
  ...(googleClientId && googleClientSecret
    ? { google: { clientId: googleClientId, clientSecret: googleClientSecret } }
    : {}),
},
```

Add a "Continue with Google" button using `signIn.social({ provider: "google" })`. The sign-in page is a server component, so it checks the same two values and passes a boolean down; the button is not rendered when Google is not configured. On a one-owner or invited-people-only app the hook above still decides who may create an account, whichever button they pressed. When the app deploys, remind the user to add the production callback URL in the Google console too.

## Verify

Checked now, with no account in the database:

- Types compile, and `pnpm db:generate` run a second time reports nothing to generate.
- The generated `auth-schema.ts` and the migration SQL both show a `role` column on `user`.
- `/sign-in` and `/sign-up` answer `200` signed out and use `DESIGN.md`'s tokens.
- `GET /api/auth/get-session` answers with no session, rather than a `404` or a `500`, which shows the route handler is mounted and the secret is read.
- The user table is still empty when this step ends. If it is not, a test account has taken the admin seat: remove it before going on.
- Google branch only: with the two Google values blank, the app still starts and the sign-in page shows no Google button.

Needs an account, so not now:

- Deferred to Step 6, after the user has signed up: their row exists in the database with `role` set to `admin` (or the app's admin role), visible in `pnpm db:studio`.
- Deferred to Step 6, after the user has signed up: they sign out and sign back in with the same credentials.
- Deferred to Step 6, after the user has signed up: one-owner apps — a second `POST` to `/api/auth/sign-up/email` is refused with `403`, and the user count stays the same.
- Deferred to Step 6, after the user has signed up: Google branch only — "Continue with Google" completes the round trip on localhost. On an open sign-up app this creates an account, so the person does it, not the builder.

Invitations and roles (not yet built with this skill, so none of these has ever been seen passing). Deferred to Step 6, after the user has signed up; `references/verify.md` has the fixture rules:

- A `POST` to `/api/auth/sign-up/email` with an email that has no invitation is refused, and the user count stays the same.
- An invitation created through the app's own invite function lets that email, and only that email, create an account, and the new row carries the invitation's role.
- A used or expired token shows the sentence, not the form.
- A signed-in member without the admin role gets a `404` from the system page and a refusal from the role-change function.
- The last admin cannot be demoted.
